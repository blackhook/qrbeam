# QRBeam 离线光学文件传输设计规格

## 1. 文档状态

- **状态：** 已批准设计
- **日期：** 2026-08-04
- **项目目录：** `/Users/blackhook/ai/openclaw/qrbeam/`
- **工作名称：** QRBeam

本文中的 `MB` 采用十进制定义，即 `1 MB = 1,000,000 B`。`KiB` 采用二进制定义，即 `1 KiB = 1024 B`。首版文件大小硬上限为 `100,000,000 B`。

## 2. 背景与目标

QRBeam 用连续变化的二维码，将电脑上的文件通过屏幕和手机摄像头传到手机。文件数据不经过互联网、局域网、蓝牙或云服务。

首版需要支持：

- 电脑网页发送文件；
- Linux CLI 在终端内连续刷新二维码；
- iOS 和 Android 原生 App 接收；
- 手机网页和 PWA 接收；
- 最大 100 MB 的文件；
- 丢帧、乱序、重复帧和局部损坏下的持续恢复；
- 类似 FlashGet 的文件区块图；
- 发送端按帧或按文件区块定位、后退和回补；
- 根据发送电脑、显示设备、输出方式和手机解码能力使用不同带宽档位。

首版不包含：

- 手机向电脑发送文件；
- 通过电脑摄像头或麦克风建立返回通道；
- 手机自动通知电脑停止；
- 云端中继、用户账号或传输记录同步；
- 超过 100 MB 文件的体验保证；
- 自动打开或执行接收到的文件。

手机确认文件完整后显示「接收完成」。用户随后在网页或 CLI 手动停止发送。

### 2.1 参考实现

设计参考 [`bashalarmistalt/decimen-optical-transfer`](https://github.com/bashalarmistalt/decimen-optical-transfer) `v0.3.0`（提交 `29cba8f`）。该项目已经验证了 LT 喷泉码、动态 QR、ZXing WASM Worker 池和 PWA 离线传输的可行性。QRBeam 采用其 QR 显示与手机 Web 解码经验，但保留分段 RaptorQ、区块回补、Linux CLI、原生 App 和 100 MB 磁盘化接收方案。

完整对比见 [Decimen 与 QRBeam 方案对比](../../research/2026-08-04-decimen-comparison.md)。

## 3. 设计原则

1. **协议一致：** Web、CLI、iOS 和 Android 使用同一个 Rust 协议核心和同一组测试向量。
2. **接收优先：** 发送端可以浪费冗余帧，但不能让偶发丢帧破坏最终文件。
3. **可观察：** 每个文件区块的进度、错误和回补地址必须对用户可见。
4. **可寻址：** 所有发送帧都有稳定身份，发送端可以暂停、后退、定位和重新生成历史帧。
5. **能力分层：** Web GUI、图片终端和 ANSI 终端不强行使用相同参数。
6. **离线可验：** 接收端只有在区块校验和最终文件校验全部通过后才报告完成。

## 4. 总体架构

```text
文件
  ↓
文件清单与分段
  ↓
系统喷泉码编码
  ↓
带身份和校验的 QR 帧
  ↓
电脑屏幕或 Linux 终端
  ↓
手机摄像头
  ↓
QR 解码、去重和区块恢复
  ↓
区块校验与最终文件校验
  ↓
保存或分享文件
```

### 4.1 组件边界

| 组件 | 职责 | 技术方向 |
|---|---|---|
| `protocol-core` | 清单、分段、RaptorQ、帧格式、CRC32C、BLAKE3、确定性调度 | Rust |
| `sender-cli` | Linux 终端发送、输出能力检测、快捷键、时间轴 | Rust |
| `web` | Web GUI 发送、手机 Web/PWA 接收 | TypeScript + WASM |
| `mobile` | iOS/Android 相机管线、区块图、后台恢复、文件保存 | Flutter + Rust FFI |

Rust 核心编译为原生库和 WASM。Flutter 只负责相机、存储和界面，Web 只负责浏览器能力与界面，不复制协议实现。

## 5. 传输模型

### 5.1 文件清单

发送数据前先以最稳健档位连续发送 `3 秒` 文件清单。稳定档默认 8 FPS，因此启动阶段发送 24 个清单帧。接收端拿到并校验清单后才能创建接收会话。

清单包含：

- 协议版本；
- 128 位随机会话 ID；
- 文件 ID；
- 经过清理的文件名；
- MIME 类型；
- 精确文件字节数；
- 传输容器字节数；
- 压缩模式（`none` 或 `gzip`）；
- BLAKE3 文件哈希；
- 按传输容器区块顺序排列的 CRC32C 列表；
- `512 KiB` 默认区块大小；
- `256 B` 原子编码符号大小；
- 区块数量；
- 最后一个区块的实际长度；
- RaptorQ 参数和确定性编码种子；
- 发送端可用的画面配置；
- 清单自身的 CRC32C。

清单使用确定性二进制字段顺序编码，并拆成不超过 1 个稳定档原子符号的片段。每个片段携带片段序号、片段总数和完整清单的 BLAKE3。接收端收齐并校验全部片段后才接受清单。

发送端在正式传输中每 `2 秒` 至少插入 1 个稳定通道清单帧。手机晚进入、短暂离开画面或重新打开接收页时，不需要电脑重新开始。

### 5.2 分段与系统喷泉码

- 文件默认按 `512 KiB` 分成独立区块。100 MB 文件有 191 个区块，适合用区块图展示。
- 每个区块按 `256 B` 分成原子符号。
- 每个区块独立使用系统喷泉码（Systematic Fountain Code）。首轮优先发送原始符号，后续持续生成修复符号。
- QR 帧载荷可以装入 1 个或多个原子符号，因此不同二维码版本仍属于同一个数据池。
- 手机不必找回某个指定丢失帧。一个区块获得足够多的原始符号或修复符号后即可恢复。
- 区块独立恢复，避免 100 MB 文件整体进入内存，也允许只回补缺失区块。

首版锁定 [`cberner/raptorq`](https://github.com/cberner/raptorq) `2.0.1`。它是 RFC 6330 的 Rust 实现，使用 Apache-2.0 许可证。Cargo 依赖使用精确版本 `raptorq = "=2.0.1"`。如果该版本无法通过 WASM、iOS 或 Android 构建验证，必须先修订本规格，不能静默替换编码算法或依赖版本。

### 5.3 帧身份

每个 QR 帧至少包含：

```text
magic
protocol_version
frame_type
session_id
file_id
channel_id
profile_id
global_frame_index
segment_index
first_symbol_id
symbol_count
payload_length
payload
crc32c
```

`frame_type` 区分清单、测试、数据、修复和控制帧。`global_frame_index` 是用户看到的显示时间轴地址；同一显示时刻的所有通道使用相同 `global_frame_index`，由 `channel_id` 区分。`segment_index` 和符号范围用于区块恢复与去重。

发送端保留帧元数据时间轴，不保留所有二维码图片。历史二维码由文件、会话种子和帧元数据重新生成。

档位、FPS、QR 版本、显示布局和通道数量都是逐帧字段。用户调速或发送端自动降档时不得创建新文件会话，手机必须继续使用已有区块和符号。只有文件、协议版本、分段参数或编码种子变化时才创建新会话。

### 5.4 确定性调度与回补

首次发送按区块顺序发送系统符号，随后进入循环修复轮次。每个修复轮次依次覆盖所有未指定的区块，并为每个区块生成新的修复符号。

发送端支持：

- 按实际历史帧后退或前进；
- 输入全局帧号定位；
- 输入区块号定位到该区块最近的发送窗口；
- 对指定区块持续生成新的修复符号；
- 回到文件清单并从首轮重新开始。

手机在某个区块连续 `10 秒` 没有增加唯一编码符号时显示建议地址，例如「区块 184，建议从帧 23900 前 100 帧开始回补」。重复帧会被去重，不会覆盖已确认数据。

### 5.5 文件容器与压缩

文件容器保留文件名、MIME 类型、原始长度、传输长度、压缩模式和原始文件 BLAKE3。

- 视频、JPEG、PNG、WebP、压缩包、Office Open XML 和 OpenDocument 默认不尝试 gzip；
- 其他格式以流式 gzip 生成候选容器；
- 只有压缩结果连同容器开销至少缩小 `1%` 时才使用 gzip；
- Web 发送端把压缩候选写入 OPFS，回退到 IndexedDB；CLI 写入临时文件；
- Web 端没有足够临时存储时跳过压缩，直接流式发送原始文件；
- 不允许为了比较压缩效果而在内存中同时保留多个完整文件副本；
- 手机完成光学恢复后解压，并对原始文件计算 BLAKE3。

## 6. 画面与带宽配置

### 6.1 单个二维码的上限

单个标准 QR Code 最高为 Version 40。其二进制载荷存在固定上限：L 级纠错约 `2953 B`，M 级纠错约 `2331 B`。继续放大同一个 Version 40 二维码只能提高识别稳定性，不能继续增加单码数据量。

所有发送后端固定使用 QR mask 4，避免每帧执行 8 个 mask 的评分。QR 模块先栅格化为 1 像素黑白矩阵，再按整数倍放大；Canvas 和图片终端必须关闭图像平滑，禁止产生灰色模块边缘。

因此，发送配置同时考虑：

- QR 版本；
- 纠错等级；
- 每模块实际显示像素数；
- 单帧符号数量；
- FPS 和单帧停留时间；
- 并行二维码通道数量；
- 通道布局。

### 6.2 稳定通道与加速通道

Web GUI 和支持图片协议的终端可以使用一个大尺寸稳定通道，并利用剩余像素显示加速通道：

```text
┌──────────────────┬─────────┐
│                  │ 加速 B  │
│    稳定通道 A     ├─────────┤
│                  │ 加速 C  │
└──────────────────┴─────────┘
```

- 稳定通道使用较大的模块、较强纠错和较低 FPS。
- 加速通道使用更高 QR 版本、更高 FPS 或较弱纠错。
- 每个通道发送不同的有效符号，拥有独立通道号和帧号。
- 手机按固定画面区域并行解码，只累计成功识别的通道。
- 加速通道失败不会阻塞稳定通道。
- 屏幕像素不足时只启用稳定通道。

标准画面候选包括 `1×1`、`2×1` 和 `2×2`。稳定通道要求每个 QR 模块至少占 `6×6` 个发送屏幕物理像素，加速通道至少占 `4×4` 个物理像素。达不到阈值的通道不得启用。

### 6.3 初始档位

以下参数是协议默认候选，不是对所有硬件的速度承诺：

| 档位 | 每帧原子符号数 | 纠错等级 | 目标 FPS | 主要用途 |
|---|---:|---:|---:|---|
| 稳定 | 1 | M | 8 | 控制信息、ANSI CLI、保底通道 |
| 均衡 | 5 | L | 24 | 普通显示器、手机 Web/PWA |
| 高速 | 8 | L | 30 | 原生 App、Web GUI |
| 极速 | 10 | L | 60 | 高刷新率屏幕与条件良好的原生 App |

每个原子符号为 `256 B`。帧编码器根据头部和符号总长度选择能够容纳数据的最低 QR 版本。发送端自检不通过时只能向更低档位降级，不能修改档位中的符号数、纠错等级或协议身份。

每个二维码默认至少显示 2 个物理刷新周期。因此 60 Hz 屏幕最多使用 30 FPS，120 Hz 屏幕才允许 60 FPS。实际档位 FPS 取协议档位上限、显示刷新率一半和发送端渲染上限三者的最小值。

最终有效吞吐按成功解码的数据计算，不按发送端理论载荷计算。

## 7. 双侧性能模型

### 7.1 发送端能力

发送端在显示文件清单前执行本地自检：

```text
发送上限 = min(
  QR 编码速度,
  Canvas 或终端输出速度,
  屏幕实际刷新率 ÷ 2,
  屏幕可用像素,
  用户设置上限
)
```

Web GUI 测量：

- 全屏物理像素、设备缩放比例和可用画面区域；
- `requestAnimationFrame` 的实际刷新率和抖动；
- 单帧编码、WASM 交换和 Canvas 绘制耗时；
- 后台降频或连续丢失显示时限；
- 每个候选布局的模块像素数。

Linux CLI 测量：

- 终端行列数和字符宽高比；
- Kitty Graphics、Sixel 或 ANSI 能力；
- 一帧编码与输出耗时；
- 连续输出积压；
- CPU 占用和调度抖动。

输出方式的默认边界：

| 输出方式 | 默认 FPS 上限 | 最大通道数 |
|---|---:|---:|
| Web GUI 全屏 | 60 | 3 |
| Kitty/Sixel CLI | 30 | 2 |
| ANSI 字符 CLI | 12 | 1 |

发送端按 `5 秒` 滑动窗口统计显示时限。如果错过时限的帧超过 `2%`，立即降低 1 个档位或关闭最低优先级加速通道；如果连续 `10 秒` 低于 `0.5%`，允许恢复 1 个档位，但不能超过本次自检上限。这个调整只依据发送端性能，不需要手机反馈。

Web GUI 和图片终端使用最多 4 帧的有界预生成队列。显示循环只消费下一帧并补充 1 帧；如果落后超过 3 个帧间隔，直接从当前时间重新排期，不进行追赶式突发播放。ANSI CLI 同样禁止积压多帧写入终端。

### 7.2 接收端能力

启动清单结束后，发送端依次显示稳定、均衡、高速和极速测试帧，每档持续 `1 秒`，最后再显示 `1 秒` 稳定帧用于重新锁定。手机按通道统计：

- 识别成功率；
- 连续丢帧长度；
- 单帧解码耗时；
- 有效吞吐；
- 最近 10 秒稳定吞吐；
- 相机曝光、对焦和画面区域是否稳定。

没有返回通道时，手机不能改变电脑正在显示的配置。它会：

- 某个加速通道在 `3 秒` 窗口内识别成功率低于 `30%` 时，暂停该通道解码 `10 秒`，随后重试；
- 始终保留稳定通道；
- 累计所有成功识别的符号；
- 显示测得的最高带宽、稳定带宽和推荐操作；
- 在用户降低电脑速度或切换布局后重新评估。

### 7.3 手机 Web 相机与解码管线

手机 Web/PWA 不依赖 `BarcodeDetector`，统一使用 ZXing-C++ WASM。原生 App 使用同一 ZXing-C++ 解码语义的原生绑定，协议解析和 RaptorQ 仍由 Rust 核心完成。

- 相机帧优先由 `requestVideoFrameCallback` 驱动；
- 每个相机流带代际编号，旧回调不得进入新流；
- iOS 先请求精确 FPS，失败后请求理想 FPS，并以 `getSettings()` 返回值为准；
- 支持时启用连续自动对焦，不启用会增加屏幕眩光的闪光灯；
- 解码 Worker 池默认 2 个槽位，上限为 `max(1, min(4, CPU 逻辑核心数 - 1))`；
- 多通道画面按固定区域裁剪后提交到 Worker；
- 所有 Worker 忙时直接丢弃当前相机帧，不排队处理陈旧画面；
- iOS 拒绝实时修改相机约束时保留当前流，并提示重启接收器后生效。

Worker 池大小、相机分辨率和相机 FPS 可以在不中断文件会话的前提下调整。手机显示实际相机参数，不显示未经验证的请求参数。

## 8. 用户界面

### 8.1 Web GUI 发送端

开始前显示文件名、大小、哈希计算进度、发送端自检结果和预计画面档位。开始后进入全屏发送界面：

- 二维码通道占据主要区域；
- 边缘 HUD 显示会话、帧号、区块号、档位、FPS 和已发送时间；
- 时间轴支持拖动定位；
- HUD 可以隐藏，避免影响手机取景。

Web 构建同时生成 Hosted PWA 和自包含的 `qrbeam-send.html`。自包含发送页内联协议 WASM、二维码生成器和样式，可直接复制到离线电脑使用，不依赖 Web 服务器。

快捷键：

| 按键 | 行为 |
|---|---|
| `Space` | 暂停或继续 |
| `J` / `L` | 后退或前进 100 帧 |
| `Shift+J` / `Shift+L` | 后退或前进 1000 帧 |
| `[` / `]` | 降低或提高发送档位 |
| `G` | 定位到帧号或区块号 |
| `R` | 循环回补当前区块 |
| `Home` | 重新发送清单并从首轮开始 |
| `H` | 显示或隐藏 HUD 与快捷键帮助 |

### 8.2 Linux CLI 发送端

基本入口：

```bash
qrbeam send <file>
```

CLI 使用终端备用屏幕和固定光标区域，避免输出滚屏。它自动选择：

1. Kitty Graphics；
2. Sixel；
3. ANSI 半块字符。

用户可以通过参数锁定输出方式或最大档位。运行中使用与 Web GUI 一致的暂停、定位、回补和调速按键。退出时恢复终端状态。

### 8.3 手机接收端

接收流程：

1. 请求相机权限并显示取景辅助框；
2. 识别文件清单；
3. 检查可用存储空间；
4. 创建临时会话与文件区块图；
5. 接收、去重、恢复和校验区块；
6. 最终校验通过后显示「接收完成」；
7. 用户保存或分享文件，并在电脑上手动停止。

区块图状态：

- 灰色：尚未收到；
- 黄色：部分完成；
- 绿色：区块恢复且 CRC32C 通过；
- 红色：区块恢复失败或校验失败，需要回补。

点击区块显示区块号、已收符号数、所需符号数、最近帧号和建议回补地址。

状态区显示瞬时带宽、最近 10 秒稳定带宽、各通道成功率、已恢复大小、剩余大小和预计完成时间。

总体进度按各区块收到的唯一编码符号数和 RaptorQ 预计冗余计算，并在解码完成前封顶 `99%`。不能只统计绿色区块数量，因为区块可能在接近完成时一次性恢复，单纯展示已恢复区块会让进度长期停滞后跳变。

## 9. 存储与恢复

### 9.1 原生 App

- 分段直接写入应用临时目录，不在内存中保存完整文件。
- 区块状态和接收符号索引写入轻量会话数据库。
- App 进入后台后保存会话；重新进入时验证临时文件与状态后继续。
- 完成后由系统文件选择器保存或分享。

### 9.2 Web/PWA

- 优先使用 Origin Private File System (OPFS)；
- 不支持 OPFS 时使用 IndexedDB 分段存储；
- 开始前通过浏览器存储估算检查配额；
- 所需可用空间至少为文件大小的 `1.3 倍`；
- 最终通过下载或 Web Share API 导出；
- PWA 资源安装完成后，传输流程可以在断网状态运行。

手机 Web 接收页必须运行在 HTTPS 安全上下文或已安装 PWA 中。首版不支持从 `file://` 打开的 standalone receiver 页面获取手机摄像头。

浏览器无法保证足够配额时必须在传输前说明，不允许静默退化为把整个文件放入内存。

## 10. 完整性、安全与隐私

- 标准二维码纠错负责局部视觉错误修复；
- CRC32C 用于帧和区块的快速完整性校验；
- BLAKE3 用于最终文件完整性校验；
- 文件名必须去除路径分隔符、控制字符和平台保留名；
- 接收到的文件不自动打开或执行；
- 传输数据不发往服务器，也不写入分析日志；
- 光学传输不提供天然保密性，旁边的其他摄像头可能看到二维码；
- 首版不实现加密。未来可以在喷泉码编码前增加基于口令的端到端加密，不改变帧传输层。

Decimen 使用 MIT 许可证。如果实现阶段复制或实质改写其代码，必须把 Evan Crawley 的版权声明、MIT 许可正文、来源文件和参考提交写入 `THIRD_PARTY_NOTICES.md`。只采用设计经验时不复制其名称、图标或视觉素材。

## 11. 异常处理

| 场景 | 行为 |
|---|---|
| 清单丢失 | 等待每 2 秒插入的清单帧，不创建未知会话 |
| 帧 CRC 失败 | 丢弃该帧，不更新区块状态 |
| 帧重复 | 去重后忽略 |
| 帧乱序 | 按区块和符号身份写入 |
| 相机失焦或未完整入镜 | 根据成功率和定位点显示明确提示 |
| 区块连续 10 秒没有增加唯一编码符号 | 高亮区块并给出帧号或区块号回补建议 |
| 临时存储不足 | 开始前阻止传输 |
| App 或页面中断 | 保留会话并在重新进入后验证恢复 |
| 新会话进入画面 | 不自动替换当前会话，要求用户确认 |
| 最终哈希失败 | 不报告完成，回到区块校验与回补状态 |

## 12. 测试策略

### 12.1 协议测试

- Rust 原生、WASM、iOS 和 Android 使用相同黄金测试向量；
- 覆盖空文件、非整区块文件、最大区块数和最大帧载荷；
- 覆盖清单、系统符号、修复符号和所有帧类型；
- 对每个字段执行边界值和损坏输入测试；
- 验证同一会话与帧地址可以确定性重建相同载荷。
- 固定 mask 4、QR 版本选择和模块矩阵使用黄金测试向量；
- 档位变化、布局变化和通道变化不得改变文件会话；
- gzip 容器与无压缩容器使用相同原始文件 BLAKE3；
- 发送调度器验证至少 2 个刷新周期、无追赶突发和有界预生成队列；
- Worker 池验证忙时丢帧、缩容时槽位身份稳定和旧相机回调失效。

### 12.2 信道模拟

模拟器按可重复种子注入：

- 0%～50% 随机丢帧；
- 连续突发丢帧；
- 重复和乱序；
- 单比特和多比特损坏；
- 通道独立失败；
- 档位和布局运行中变化。

只要持续存在可解码通道，发送端继续生成新修复符号时，接收端必须最终完成。

### 12.3 真实设备测试

发布测试至少覆盖：

- 1 台 iPhone 原生 App；
- 1 台 Android 原生 App；
- iOS Safari/PWA；
- Android Chrome/PWA；
- 1080p 和 4K 显示器；
- 普通 ANSI 终端；
- 至少一种 Kitty Graphics 或 Sixel 终端。

测试报告记录设备、屏幕分辨率、刷新率、距离、环境光、布局、档位、稳定吞吐和最终哈希，不用单一设备结果替代协议正确性测试。

## 13. 验收标准

1. `1 B`、`1 KB`、`1 MB`、`10 MB` 和 `100 MB` 文件逐字节还原，最终 BLAKE3 完全一致。
2. 信道模拟存在 50% 随机丢帧、重复和乱序时，持续发送仍能完成。
3. 任意载荷帧被修改后不会进入有效区块。
4. Web、CLI、iOS 和 Android 的协议黄金测试向量完全一致。
5. 普通 ANSI 终端可以使用稳定档发送，图片终端和 Web GUI 可以启用加速通道。
6. 手机区块图和吞吐统计更新时不阻塞相机解码。
7. 接收端中断后可以恢复已经校验完成的区块。
8. PWA 或 App 准备完成后，关闭网络仍可完成传输。
9. 手机只有在所有区块和最终文件校验通过后显示「接收完成」。
10. 用户可以暂停、前后移动、按区块定位并循环回补。
11. 60 Hz 发送屏幕默认不超过 30 FPS，120 Hz 屏幕才允许 60 FPS。
12. `qrbeam-send.html` 在无网络环境可以选择文件并开始发送。

## 14. 实现顺序约束

实现应先完成协议与模拟信道，再接入真实二维码和相机：

1. 协议核心、帧身份和确定性时间轴；
2. 分段 RaptorQ 与文件恢复；
3. 信道模拟、区块图数据模型和回补；
4. 固定 mask QR 生成、显示调度和 ZXing Worker 接收管线；
5. Web GUI、Standalone 发送页与 Web/PWA 接收；
6. Linux CLI 输出后端；
7. Flutter iOS/Android 接收端；
8. 发送端与接收端性能自检；
9. 真实设备兼容性和性能优化。

任何性能优化不得改变帧身份、完整性校验或跨平台测试向量。
