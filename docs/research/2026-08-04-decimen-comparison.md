## 2. Decimen 的实际实现

Decimen 是一个完整的纯 Web/PWA 实现：

```text
文件或文本
  → 可选 gzip
  → 文件容器与 SHA-256
  → 整体 LT 喷泉码
  → 单个动态 QR Code
  → 手机摄像头
  → ZXing WASM Worker 池
  → LT 剥离解码
  → SHA-256 校验和下载
```

关键实现：

- 用稳健孤子分布（Robust Soliton Distribution）实现 LT 喷泉码；
- 帧序号决定伪随机块集合，发送端和接收端独立得出同一集合；
- 20 字节小端帧头携带会话、序号、块数、块长、总长和 FNV-1a；
- 单个文件作为一个喷泉码对象，最多 64 MiB；
- QR 默认 Version 40、ECC L、2953 B/帧、60 FPS；
- 固定 QR mask 4，跳过 8 个 mask 的逐一评分；
- 预生成少量二维码，显示线程只取下一帧；
- `requestAnimationFrame` 落后时不补发突发帧；
- 接收端用 `requestVideoFrameCallback` 获取相机帧；
- ZXing-C++ WASM 在 Worker 池解码，Worker 忙时直接丢弃新相机帧；
- iOS 先请求 `exact` FPS，再退回 `ideal`，并以 `getSettings()` 为准；
- Android 能力优先探测，支持时启用连续自动对焦；
- 通过 PWA、Hosted Web 和单文件 HTML 提供离线使用方式；
- 最终文件以 SHA-256 校验，文件名在发送和接收两端都做清理。

参考仓库记录了约 128～130 KB/s 的近距离手机对手机结果。它同时明确说明：2953 B/帧、60 FPS 是 120 Hz 屏幕的最佳情况；普通电脑显示器更适合约 1465 B/帧、24～30 FPS。

## 3. 能直接借鉴的设计

### 3.1 QR 生成与显示

QRBeam 采用以下 Decimen 经验：

- QR mask 固定为 4，避免每帧执行 8 次 mask 评分；
- QR 模块先生成 1 像素矩阵，再按整数倍放大；
- Canvas 禁用图像平滑，避免模块边缘变灰；
- 每个二维码至少跨越 2 个显示刷新周期；
- 发送端保留有界预生成队列；
- 显示循环落后时丢弃显示时隙，不追赶式突发播放；
- 全屏采用页面布局状态，不依赖容易触发 Safari 颜色取样问题的固定遮罩层。

### 3.2 手机 Web 解码管线

QRBeam 采用以下接收策略：

- Web 端使用 ZXing-C++ WASM，不依赖 Safari 缺失的 `BarcodeDetector`；
- 相机帧通过 `requestVideoFrameCallback` 驱动；
- 解码 Worker 池采用固定槽位；
- 所有 Worker 忙时直接丢帧，不排队处理已经过时的画面；
- 相机流使用代际编号，防止旧回调在新相机流中复活；
- iOS 先请求精确 FPS，失败后请求理想 FPS；
- 始终显示相机实际分辨率和实际 FPS；
- 支持时启用连续自动对焦，不启用会增加屏幕反光的闪光灯；
- iOS 拒绝实时修改约束时保留当前传输，不重启相机。

### 3.3 协议与测试纪律

QRBeam 采用以下工程实践：

- 帧协议必须有黄金字节向量，不能只做编码器和解码器互测；
- 任意影响随机符号选择的计算都属于线协议；
- 会话身份覆盖全部固定协议字段，而不是只比较会话 ID；
- 帧重复、乱序和随机丢失必须有确定性测试；
- 文件名在接收端再次清理；
- 压缩只在确定减少传输字节时采用，并跳过 JPEG、视频、压缩包等已压缩格式；
- PWA 构建必须把 WASM、Worker 和应用资源加入离线缓存。

## 4. 不能直接照搬的部分

| 维度 | Decimen v0.3.0 | QRBeam 需求 | 处理决定 |
|---|---|---|---|
| 文件上限 | 64 MiB | 100 MB | 使用磁盘分段和 100,000,000 B 硬上限 |
| 内存模型 | 发送和接收都持有完整文件及中间副本 | 100 MB 且需要可恢复 | 分段写临时存储，不持有完整冗余对象 |
| 喷泉码 | 整个文件使用 1 个 LT 对象 | 区块图、定向回补、跨端统一 | 每个 512 KiB 区块独立使用 RaptorQ |
| 进度 | 估算已收帧，完成前不展示真实文件区块 | FlashGet 式区块图 | 展示区块状态，同时用唯一编码符号数估算总体进度 |
| 回补 | 继续接收任意新帧，没有区块定位 | 支持帧定位、提前 100 帧、指定区块循环 | 保留确定性时间轴和区块修复模式 |
| 设置变化 | 修改设置会新建会话，接收端重置 | 调速不能丢失已有进度 | 档位、布局和通道是逐帧字段，不改变文件会话 |
| 发送界面 | 单个 Web QR | Web GUI、ANSI CLI、Kitty/Sixel、多通道 | 共用协议，不同输出后端独立自检 |
| 手机端 | Web/PWA | Web/PWA、iOS App、Android App | Flutter 外壳 + Rust FFI；Web 继续用 WASM |
| QR 通道 | 单二维码 | 大稳定码 + 可选加速码 | 每通道独立编号，任何成功帧都进入同一文件区块池 |
| 参数选择 | 用户手工选择 bytes/frame 和 FPS | 发送电脑性能也要自动考虑 | 发送端测编码、绘制、终端输出、分辨率和刷新率 |
| 持久化 | 文件主要在内存，结束后 Cache API 服务媒体 | 中断恢复和 100 MB | 原生临时文件；Web 使用 OPFS/IndexedDB |
| 完整性 | 帧流 FNV-1a + 文件 SHA-256 | 分段状态和最终强校验 | 帧/区块 CRC32C + 最终 BLAKE3 |
| 自动停止 | 无返回通道，发送无限循环 | 手机完成后用户手动停止 | 与 Decimen 保持一致 |

## 5. 编码方案的取舍

Decimen 的 LT 实现短小、可读，实测有效，但它以整个文件作为一个解码对象。其剥离解码的已解决块数在后期快速增长，因此不能直接提供用户要求的稳定区块图和定向回补。

QRBeam 保留已批准的分段 RaptorQ 设计：

- 每个 512 KiB 区块独立完成；
- 原始符号和修复符号都可用于恢复；
- 区块可以独立校验、持久化和回补；
- 100 MB 文件不会形成一个巨大的内存解码图；
- 修改显示档位不会改变已经接收的区块状态。

Decimen 的 LT 黄金向量和确定性数学处理仍作为 QRBeam 测试纪律的参考，但不复制为 QRBeam 的线协议。

## 6. 速度模型修订

Decimen 源码指出，二维码至少显示 2 个刷新周期更可靠。QRBeam 因此采用：

```text
实际发送 FPS ≤ 显示刷新率 ÷ 2
```

默认行为：

- 60 Hz 电脑显示器最多使用 30 FPS；
- 120 Hz 显示器才允许 60 FPS；
- ANSI CLI 还要受终端写入和重绘耗时限制；
- 发送循环落后时跳过时隙，不补发突发帧；
- 手机统计成功识别后的有效带宽，不把理论 FPS 当成带宽。

Decimen 的公开经验值作为初始标尺：

- 2953 B/帧适合近距离、高分辨率和高刷新率发送屏幕；
- 1465 B/帧是普通显示器的安全起点；
- 24～30 FPS 是 60 Hz 显示器的合理范围；
- 更大的物理二维码主要提升模块可辨识度；达到 Version 40 后，额外像素应分配给加速通道，而不是继续放大单码载荷。

## 7. 文件容器修订

QRBeam 增加 `none` 和 `gzip` 两种容器压缩模式：

- 视频、JPEG、PNG、WebP、压缩包、Office Open XML 和 OpenDocument 默认跳过 gzip；
- 其他格式使用流式 gzip 生成候选结果；
- 只有压缩结果连同容器开销至少缩小 `1%` 时才使用 gzip；
- Web 端把压缩候选写入 OPFS，不支持时回退到 IndexedDB；CLI 写入临时文件，避免同时保留多个 100 MB 副本；
- 清单同时记录原始长度、传输长度、压缩模式和原始文件 BLAKE3。

## 8. 离线交付修订

除 Hosted PWA 外，QRBeam 需要生成：

- `qrbeam-send.html`：自包含 Web 发送端，适合直接复制到离线电脑；
- Linux 单文件 CLI；
- iOS 和 Android 原生 App；
- 可安装的手机接收 PWA。

手机浏览器从 `file://` 打开的单文件页面不能可靠取得相机权限，因此首版不把 standalone receiver HTML 作为移动端正式入口。
